# 串口助手正常但 recv.py 无数据


## 1. 当前结论

DTR/RTS 显式处理仍在当前 recv.py 链路中。当前串口参数以 app_config.h 的 USART1 460800 为准；115200 仅是历史调试环境。


## 2. 问题概述

串口助手能收到数据、`recv.py` 却一个字节都收不到

> **类型**：主机侧串口配置 / 硬件信号线问题（不是 Python 代码 bug），发生在 D2 用合成信号桩函数验证"1 kHz 采样 → 攒窗 → 打帧 → PC 落盘"整条链路的阶段。

### 2.1 编号 / 标题

Q-03 — 正点原子 XCOM 串口助手能收到数据、Hex 也能看到帧头，关掉助手后运行 `recv.py` 一个字节都收不到。

### 2.2 时间 / 阶段

2026-09-21；D2（采集链路联调）。固件侧 `app_sample.c`（1 kHz TIM3 + 双缓冲）、`link_frame.c`（打帧）、`main.c` 均已写好且编译通过（`0 Error(s), 38 Warning(s)`），数据源为合成信号桩函数（45 Hz/0.05 g + 90 Hz/0.01 g）。

### 2.3 现象（原文）



> "串口调试助手能接收到信息，转成hex也能看到表头，但关掉串口助手后，运行recv.py无法接收到数据，我核对过串口是com13波特率也是460800"

### 2.4 排查过程



1. **先排除"COM 号 / 波特率写错"**：重新枚举串口，确认 `COM13 = USB-SERIAL CH340 (VID 1A86 / PID 7523)`，正是板载串口，与 `recv.py` 的 `PORT`、固件 `APP_UART_BAUD`(460800) 完全一致 → 参数无误。同时发现 XCOM 进程仍在后台运行（**关窗口 ≠ 退出进程**），但实测它**不阻塞** Python 打开端口，故不是"端口被占用"。
2. **关键一步：绕开帧解析，直接裸读字节流**。用 `serial.Serial('COM13', 460800)` 打开成功后连续读 4 秒 → **收到 0 字节**。这一步把问题范围从"Python 解析逻辑有 bug"缩小到"数据根本没上来"。
3. **分四种组合测 DTR / RTS 控制线**（每种读 2.5 秒）：

| DTR | RTS | 收到字节  | 结论      |
| --- | --- | ----- | ------- |
| 0   | 0   | 6243  | 正常      |
| 0   | 1   | **0** | **收不到** |
| 1   | 0   | 4162  | 正常      |
| 1   | 1   | 4186  | 正常      |

4. **显式把两条线置 0 后立刻恢复，并且板子重启了**（帧序号从 1 重新开始）→ 反证此前芯片确实处于被复位状态。
5. 用同一套设置端到端复跑：`recv.py` 收 20 帧、丢帧 0；`plot_check.py` 谱峰 44.92 Hz / 0.0497 g 与 89.84 Hz / 0.0098 g、幅值比 5.06 : 1，与桩信号设定（45 Hz / 0.05 g + 90 Hz / 0.01 g）一致。

### 2.5 根本原因



- 探索者板载 CH340 的"一键下载"电路把 **RTS→NRST、DTR→BOOT0**。当线状态停在 **DTR=0 且 RTS=1**（即串口 ISP 下载模式的保持状态）时，**NRST 被持续拉低，MCU 一直处于复位中**，程序根本没有运行，自然一个字节都不发。
- **pyserial 打开端口时不会主动去驱动这两条线**，而是沿用驱动里已有的状态。串口助手退出时若把它们留在了上述状态，`recv.py` 就会表现为"端口打开成功、却零字节"。

### 2.6 解决方法（已落地）



在 `03_Python工具\recv.py` 打开串口之后、`ser.reset_input_buffer()` 之前加两行：

```python
    ser.dtr = False
    ser.rts = False
```

配套纪律：跑 `recv.py` 之前把串口助手**彻底退出**（托盘图标右键退出），并保持 XCOM 里的 DTR / RTS 复选框不勾选。

### 2.7 验证结果



- `python recv.py` → 20 帧全部收到、**丢帧 0**，落盘 `04_数据集\raw\X_0033_0052.csv`（20480 个样本）；
- `python plot_check.py` → 第 1 峰 **44.92 Hz / 0.0497 g**（bin 46）、第 2 峰 **89.84 Hz / 0.0098 g**（bin 92）、幅值比 **5.06 : 1**、交流 RMS 0.0360 g，与桩信号设定一致（频率读数落在 44.92 而非 45.00 属正常，来自 0.977 Hz/格 的频率分辨率）；图存 `05_演示与输出\X_0033_0052_spectrum.png`；
- 顺带印证了设计参数：稳态每秒自检约 **957 点**（开机第一秒为 999 点），与"每发一帧暂停采样约 45 ms（2057 B @ 460800）"的预算吻合，**不是丢数**。

### 2.8 经验与可复用点



- **口诀**："**端口打开成功但零字节 → 先怀疑信号线状态，不要改解析代码。**"
- **二分法的价值**：先用"裸读字节"把"数据没上来"与"解析逻辑有问题"切开，再往硬件 / 驱动层查——否则很容易在 Python 里白改半天。
- **串口工具不要只关窗口**：XCOM 关窗口不等于退出进程，采集前确认它彻底退出。
- **通用教训**：CH340 / CP2102 / FT232 这类 USB 转串口芯片的 DTR / RTS 常被板子拿去做复位或启动模式控制（"一键下载"电路）。Python 侧统一在 `open()` 之后显式设置这两条线，可避免"助手能收、脚本收不到"这类诡异现象。
- 与 Q-02 属同一类思维：**现象出现在 A 层，根因在 B 层**——Q-02 是"数据全 0 的根因在读函数没检查返回值"，本条是"收不到数据的根因在串口控制线"。
- **面试话术**："串口助手能收到、Python 脚本一个字节收不到。我先用裸读字节排除了解析层，再分四种组合测 DTR/RTS，定位到板载 CH340 的一键下载电路把 RTS 接到了 NRST——线停在 DTR=0/RTS=1 时芯片被按在复位上。修法是在脚本打开串口后显式把这两条线置 0，之后 20 帧连收、丢帧 0。"
