# IIC 三轴整值错乱


## 1. 当前结论

问题已通过 PB6/PB7 解决，当前 iic.h 使用该对引脚。PB8/PB9 与 Z 轴重力是排查时历史环境；当前为 X 测量轴、Y 重力轴，正式采集前仍需六面标定。


## 2. 问题概述

真实传感器三轴读数间歇性"整值错乱"（Z 读到 X 的值、平放时读不到重力）

> **类型**：硬件层总线负载 / 软件 IIC 误码（**不是传感器坏、也不是帧解析 bug**），发生在 D2 把数据源从合成桩切回真实 MPU6050 之后的采集验证阶段。

### 2.1 编号 / 标题

Q-04 — 换回真实传感器后三轴读数出现"整值跳变"式错乱（Z 轴读到 X 轴的值、平放时读不到重力、同一位置连读三次差很多），把软件 IIC 从 PB8/PB9 换到 PB6/PB7 后恢复正常。

### 2.2 时间 / 阶段

2026-09-21；D2（采集链路验证）。`iic.c` / `mpu6050.c` / `app_sample.c` / `link_frame.c` / `main.c` 均已写好且编译通过（`0 Error(s), 38 Warning(s)`），`APP_USE_FAKE_ACCEL` 已置 0（切为真实数据源）；传感器用螺丝固定在风扇一角，风扇立放。

### 2.3 现象（实测统计 + 原文）



四次采集的逐轴统计（1 kHz、1024 点/帧、20 帧）：

| 轴   | 风扇     | 最小  | 最大    | 均值      | 标准差    | 恰好为 0 的样本 |
| --- | ------ | --- | ----- | ------- | ------ | --------- |
| X   | 开（6 V） | 0   | 896   | 225.4   | 298.9  | 18.9 %    |
| X   | 关      | 0   | 896   | 281.8   | 318.7  | 17.7 %    |
| Y   | 关      | 36  | 16672 | 16422.1 | 136.8  | 0 %       |
| Z   | 关      | 0   | 15744 | 1197.5  | 4047.1 | 17.7 %    |

- 疑点 1：**20480 个样本里负样本 0 个**，而 X 轴均值只有 232~282 格（0.014~0.017 g，说明重力几乎没压在该轴上），却仍有 17.7 % 的样本精确停在 0。
- 疑点 2：**开风扇与关风扇，X 轴统计几乎完全相同**（见上表前两行）。
- 疑点 3：单看 Y 轴却完全正常（均值 16422 格 = 1.0024 g，高字节 96.7 % 为 0x40，20480 个样本里只有 1 个孤立毛刺）。

用户原文（换另一颗模块后的多姿态测试）：

> "换另一个传感器，进行多姿测试：当重力压在 Y 轴上时，数值几乎都是 16000 左右，旋转 180°，数值很快稳定在 -16000；旋转到重力在 X 轴时，Y、Z 轴的值在 0~300 之间波动，X 轴时而能读到 16000 左右的值，反转 180 后，情况类似 X 轴能读到 -16000 左右的值，但不同的是此时 Z 轴也会出现 -16000 的值；最后平放模块，使得重力在 Z 轴上时，此时三轴的读数基本都在 ±300 之间波动，X 轴偶尔会跳到 -700 左右"

> "三次读数经常差很多"

### 2.4 排查过程



1. **先用"三轴静态对照"确认读取链路本身是好的**：Y 轴静止读到 16422 格 = **1.0024 g**，高字节 96.7 % 为 0x40 → 说明突发读、高低字节拼装、量程换算、符号处理**全部正确**。据此排除"整条链路都坏了"，锁定为"**间歇性**错"。
2. **再用"三轴模长自检"证伪"被测对象在动"**：在同一安装方式、两次都静止不动的前提下，Y 轴那批数据里重力**全部**压在 Y 上（1.0024 g），Z 轴那批却读到 0.961 g → 合成模长 √(1.0024² + 0.961²) = **1.39 g**。静止物体的加速度模长必须等于 1 g，**物理上不可能** → 判定为**读数错误**，而不是风扇或夹具在动。
3. **开 / 关风扇对照**：X 轴两批统计几乎相同（最小 0、最大 896、零值约 18 %）→ **与风扇振动无关**，彻底排除"这是风扇的故障特征"。
4. **降速对照**：把 `iic_delay()` 由 `delay_us(2)` 改成 `delay_us(10)`（总线约 250 kHz → 约 50 kHz）后重测，**症状不变** → 排除"时序余量不够 / 采样点太靠前"这类经典软件 IIC 问题。
5. **换件对照**：换上另一颗模块，症状**完全相同** → 排除"这一颗传感器坏了"。
6. **连读三次对照**（`mpu6050_read_raw()` 连调三次后立即打印）：传感器静止时三次结果**经常差很多**，出现 0 与 15456 这类整值跳变 → 直接证明**读操作本身不可靠**，问题落在总线 / 驱动层。
7. **换引脚验证**：把 `iic.h` 里 SCL / SDA 的 6 个宏由 **PB8/PB9** 改到 **PB6/PB7**（一对专属引脚），其他代码一行不动 → **立即恢复正常**。

### 2.5 根本原因



- **PB8/PB9 不是一对"干净"的引脚**：板载 **24C02 EEPROM** 就挂在这条总线上，MPU6050 与它**共用走线和上拉电阻**。此前版本 曾把这一点记入 相关页面 / 相关页面，当时的判断是"从机地址 0x68 与 0x50 不冲突，可以共用"——**地址确实不冲突，但电气负载会冲突**。
- 一条总线上多挂一个器件意味着**总线电容更大、走线更长、上拉等效阻值更低**；软件 IIC（纯 GPIO 位操作，没有硬件外设的滤波与超时保护）在这种负载下会**间歇性采错位**，表现为"整值串位"（Z 读到 X 的字节）。
- 以"换引脚后立即恢复"为实测结论；究竟是电容负载、串扰还是上拉配比所致，本次未用示波器逐项测量，留待有条件时补测。

### 2.6 解决方法（已落地）



1. **把 IIC 换到专属引脚**：`00_工程文件\Drivers\BSP\IIC\iic.h` 里 6 个宏改为 PB6/PB7（`IIC_SCL_GPIO_PIN` = `GPIO_PIN_6`、`IIC_SDA_GPIO_PIN` = `GPIO_PIN_7`，两个 `..._CLK_ENABLE()` 仍为 GPIOB 时钟），接线同步挪过去。**⚠️ 待办：对照《探索者V3 IO引脚分配表》确认 PB6/PB7 在该板上确实空闲**；确认后把 相关页面 / 相关页面 的接线口径一并改为 PB6/PB7。
2. **修 `iic_init()` 里一个确定存在的 bug**：`gpio_init_struct_SDA` 只填了 `.Pin` 和 `.Mode`，`.Pull` 与 `.Speed` 是**栈上的随机值**（可能把 SDA 配成内部下拉，与外部上拉打架）。改法：

```c
gpio_init_struct_SDA = gpio_init_struct_SCL;      /* 先整体复制 SCL 那份完整配置 */
gpio_init_struct_SDA.Pin  = IIC_SDA_GPIO_PIN;     /* 只改引脚号 */
gpio_init_struct_SDA.Mode = GPIO_MODE_OUTPUT_OD;  /* 再改成开漏 */
```

3. **确立纪律：`iic_delay()` 必须保持 `delay_us(2)`**。读一次 6 字节 = 9 个字节 × 9 个时钟 = 81 个时钟周期：

| `iic_delay`    | 单次 6 字节读耗时    | 1 kHz 采样能否撑住                      |
| -------------- | ------------- | --------------------------------- |
| `delay_us(2)`  | 约 **324 µs**  | ✅ 占约 32 %，余量充足                    |
| `delay_us(10)` | 约 **1620 µs** | ❌ 超过 1 ms，主循环跟不上，实际采样率会掉到约 600 Hz |

而 FFT 仍按 1 kHz 计算频率轴，**所有频率读数都会偏大 1.67 倍**——这是最隐蔽的一类错误，务必改回 2 µs。

### 2.7 验证结果



换到 PB6/PB7 后，传感器静止、同一位置连读三次的输出（格式：三次的 `x y z` | 控制寄存器 | 器件 ID）：

```text
  432    392  17000 |    488    368  17112 |    456    284  17148 | PWR=0x01 ID=0x68
  496    388  17008 |    456    324  16976 |    516    328  17120 | PWR=0x01 ID=0x68
  444    296  17112 |    560    276  17080 |    372    292  16924 | PWR=0x01 ID=0x68
```

- `PWR_MGMT_1` 恒为 **0x01**、`WHO_AM_I` 恒为 **0x68** → 芯片没有复位、通信稳定；
- 三次连读差值只有 **30~150 格**（该芯片在 260 Hz 带宽下噪声 σ ≈ 130 格 = 0.008 g）→ **属噪声水平，不再是错误**；
- Z ≈ 16900~17150（重力压在 Z 轴上，模块平放）；
- 遗留项：三轴模长 √(432² + 392² + 17000²) = 17010 格 = **1.038 g**，比 1 g 高约 **3.8 %**（MPU6050 灵敏度容差 ±3 % 加零偏 ±60 mg 勉强可解释，但偏大）→ **列入正式采集前的"六面标定"待办**，先记录、不阻塞主线。

### 2.8 经验与可复用点



- **口诀**："**读数是整值跳变（0 变 15456）而不是小幅噪声 → 先怀疑总线和布线，别先怀疑传感器。**"
- **判据更正（重要，本条更正本项目此前用过的一条错判据）**：判断"数据是否被削波 / 错码"时，**"最小值必须是负数"这条不成立**。正确判据是看 **|均值| ÷ 标准差**：
  - 比值 > 3 时，按正态分布负样本概率 < 0.2 %，"全为正"**完全正常**（传感器有倾斜时，重力会在水平轴上留下正偏置）；
  - 比值 < 1（σ 比均值还大）却一个负数都没有，才是**真异常**；
  - 本次对照：损坏数据的 X 轴是 232 / 325 = **0.7** 却 0 个负样本 → 真异常；修好后 X 轴是 470 / 130 = **3.6** 全为正 → 正常。
- **另一条自我更正**："全部样本都是 4 的倍数"当时被当成数据链路的可疑点，实为**该芯片加速度输出的固有特性**（X、Y、Z 三轴合计 6 万余个样本 100 % 是 4 的倍数，等效分辨率 4 格 = 0.24 mg）。**统计特征要现在"已知正常的通道"上验证过，才能当异常判据用。**
- **最省事的判别手段是"连读三次对比"**：几行代码、5 分钟，就能把"读取不可靠"与"物理量真的在跳"分开——比反复改配置、换硬件高效得多。
- **"共用总线"要当成设计约束对待**：一条 I2C 上挂多个器件时，**从机地址不冲突 ≠ 电气上没影响**；软件模拟 IIC 没有硬件外设的超时 / 滤波保护，余量更小，能独占就独占。
- **配套纪律（本次调试中顺带发现的数据损失风险）**：`recv.py` 的存盘文件名是 `轴号_首帧_末帧.csv`，**不带时间戳与工况标签**，同一工况反复采集会**互相覆盖**（风扇开启的那批 20 帧 X 数据就是这样被覆盖掉的）。正式录数据集前必须给文件名加上时间戳 + 工况标签。
- **面试话术**："真实传感器换上去以后三轴读数间歇性整值错乱——Z 会读到 X 的值、平放时三轴都读不到重力。我先用三轴模长证伪了'被测对象在动'（静止时模长必须是 1 g，实测 1.39 g），再用开关风扇、降速、换件、连读三次四组对照，把传感器、时序、振动逐个排除，最后定位到 IIC 与板载 24C02 共用 PB8/PB9 造成间歇性采错位，换到专属引脚后恢复。顺带还发现读函数里一个 GPIO 结构体没填完，以及把 IIC 降速到 10 µs 会让 1 kHz 采样悄悄掉到 600 Hz 这两个坑。"
