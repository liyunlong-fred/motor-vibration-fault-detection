# 固件与 PC 软件架构


## 1. 当前实现边界

原文大量模块名是设计草案，不能当当前清单。当前实际边界以[系统地图](../../知识库/20_系统地图.md)为准：app_config.h、app_sample.c、dsp_fft.c、link_frame.c、iic.c、mpu6050.c、recv.py、frames.py、metadata.py、检查工具和 make_dataset.py。模型、特征和 UI 模块尚未落地。


## 2. 开发环境与工程结构

### 2.1 工具链

- **工程基底建议**：以正点原子官方 HAL 例程的 Keil 工程（自带时钟与 4.3″ 屏 LCD/触摸驱动）为基底，在其上添加我们的模块代码——**不要从空的 CubeMX 工程起步**，避免重配屏的大量引脚；
- **CubeMX 的角色推迟到 D8–D9**：用 CubeMX + X-CUBE-AI 生成模型 C 代码后，并入上面的 Keil 工程编译（X-CUBE-AI 官方支持 MDK-ARM 工具链）；
- PC 端算法侧：Python 3.10+（Anaconda 或 Miniconda），库：numpy、scipy、pyserial、matplotlib、scikit-learn、PyTorch（或 TensorFlow/Keras）；
- 版本管理：Git + GitHub（简历要放仓库链接）。

### 2.2 外设配置

| 外设                     | 配置                                                                                | 用途                                                                 |
| ---------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| RCC                    | HSE 外部晶振（探索者板通常 8 MHz，**以原理图为准**）→ PLL 到 168 MHz                                  | 主频拉满                                                               |
| FPU                    | 使能（Cortex-M4F）                                                                    | 浮点运算                                                               |
| IIC（软件模拟） | GPIO 位操作；SCL=PB6、SDA=PB7，保持 delay_us(2)；不使用 I2C1 外设或 DMA | MPU6050 专属总线，避免与板载 24C02 共用 PB8/PB9。 |
| USART1 | 当前 460800 baud | 板载 CH340：日志与数据上送 |
| TIM3 | 1 kHz 采样节拍 | 当前采样定时器 |
| LCD（官方例程已配）            | 引脚众多，直接照官方 LCD 例程初始化                                                              | 4.3″ 触摸屏显示（本项目 UI 画于此）                                             |
| GPIO                   | 板载 BEEP/DS0/DS1/KEY（正点原子例程宏）+ 外接继电器空闲脚                                            | 输出与交互                                                              |
| NVIC                   | 采样/通信/按键中断优先级分级                                                                   | 中断优先级：采样 > 通信 > UI                                                 |

### 2.3 目录规划

```text

├─ App/                  # ★ 你自己写的业务层（重点展示）
│   ├─ app_main.c        # 顶层状态机

│   ├─ model_infer.c     # X-CUBE-AI 生成网络调用封装

└─ tools/                # PC 端（放 Python 仓库里更清晰，见 相关页面）
```

## 3. 目标模块化架构

> 用途：回答"这个项目到底要写哪些东西、各自做什么、谁调用谁"。按 **6 层**向下拆，最底层 = **一个 .c 文件只干一件事**。纪律：上层只调下层的接口函数；层间用 `types.h` 定义的结构体传数据；参数只有一个来源（config.json ↔ algo_params.h）。

### 3.1 分层视图

```text
L5 系统    电机振动故障检测系统（离线实时 3 分类 + 报警）
L4 子系统  固件侧：采集 / 算法 / 推理 / 决策 / 交互 / 链路
           PC 侧：采集工具 / 数据处理 / 训练量化 / 评估
L3 模块    子系统内的功能模块（一个模块 ≈ 1~2 个 .c）
L2 组件    .c/.h 文件：职责 + 关键函数（见 B.1 / B.2）
L1 底座    不用自己写：HAL / CMSIS-DSP / X-CUBE-AI 生成码 / 正点原子 lcd 等 BSP / CubeMX 骨架
L0 硬件    探索者 F407（含 4.3″屏）+ MPU6050 + BEEP/LED/KEY + 继电器 + 12V 风扇实验台
```

主线数据流：`MPU6050 →(I2C+FIFO+DMA)→ 乒乓缓冲 → 加窗 → FFT → 特征 → AI 概率 → 平滑决策 → 屏/声光/继电器`；PC 侧：`串口帧 → raw 文件 → 切窗+特征 → 训练/量化 → 部署 → 评估`。

### 3.2 固件目标模块

```text
02_固件/（Keil 工程）
├─ Core / Drivers / SYSTEM …   # 官方+CubeMX+HAL：main.c、stm32f4xx_it.c、lcd.c（不自己写，只在其上扩展）
└─ App/  ★ 本项目业务层
   ├─ project_config.h    # 板级配置：引脚 / 时钟 / I2C 地址(0x68) / 波特率
   ├─ types.h            # 公共结构体（模块间唯一"数据语言"）
   ├─ algo_params.h      # 算法参数（由 gen_config_header.py 从 config.json 生成，勿手改）
   ├─ app_main.c         # 顶层状态机 + 上电初始化
   ├─ bsp_i2c.c          # I2C1 + DMA 读写封装
   ├─ bsp_mpu6050.c      # MPU6050 驱动：初始化 / 读加速度 / FIFO 批量读 / 自检
   ├─ dsp_window.c       # 生成 Hann 窗 + 加窗
   ├─ dsp_fft.c          # CMSIS-DSP 实数 FFT → 幅度谱 + 频段能量
   ├─ feat_extract.c     # 时域统计 + 频域特征 → feature_t（与 Python 同参）
   ├─ model_net.c        # X-CUBE-AI 生成的 network（工具生成，不改）
   ├─ ai_infer.c         # 推理封装：feature_t → prob_t + 耗时
   ├─ decision.c         # 平滑(EMA/多窗投票) + 滞回 → 最终状态
   ├─ ui_screen.c        # 4.3″屏页面：状态大字 / 频谱 / 统计（复用官方 lcd.c）
   ├─ act_alarm.c        # 蜂鸣器 / 继电器 / LED 动作逻辑
   ├─ link_frame.c       # 帧编解码：上行样本块 / 下行指令 + CRC
   ├─ link_uart.c        # UART + DMA 环形收发缓冲
   ├─ stream_mode.c      # "采集模式"状态机：连续采样 → 打帧上送 PC
   └─ app_debug.c        # 日志开关 / 断言 / DWT 耗时统计
```

**模块职责详解（新手向）——每张卡片统一模板：角色 / 接收 / 处理 / 发送 / 依赖 / 验收 / 类比**

> 怎么读卡片：①"角色"= 它在整条流水线上站哪个工位；②"接收 / 发送"用"谁 → 谁"标明数据从哪来到哪去；③"处理"= 它干活的具体步骤；④"验收"= 做到什么程度算它过关（对照 相关页面 的退出标准）。

#### 3.2.1 project_config.h —— 全系统的"接线地图"

- **角色**：纯配置头文件，不是干活模块；把"硬件接在哪个引脚、跑多快、地址多少"集中登记。
- **接收**：不接收运行数据；被所有底层驱动在**编译时**读取。
- **处理**：没有运行逻辑。集中定义：I2C 引脚与速率、MPU6050 地址(0x68)、串口波特率、BEEP/KEY/LED 引脚、时钟频率等。
- **发送**：把常量提供给 bsp_i2c / bsp_mpu6050 / link_uart / act_alarm / ui_screen。
- **依赖**：官方原理图（引脚合法性）。
- **类比**：整栋楼的"总配电箱图"——任何人接线前先查它，避免两个模块抢同一个引脚。
- **验收**：编译通过；改接线只需改这一个文件（阶段 D2）。

#### 3.2.2 types.h —— 模块间的"数据语言词典"

- **角色**：只定义结构体和枚举、不写逻辑；是全系统模块传递数据的**统一规格**。
- **接收 / 发送**：不接收不发送，被所有模块 `#include`。
- **处理**：定义 `accel_t`（三轴原始值）、`spectrum_t`（幅度谱）、`feature_t`（特征向量）、`prob_t`（3 类概率）、`decision_t`（结论：状态+置信度+f0）、`state_t`（正常/不平衡/机械松动）以及帧类型。
- **类比**：快递业的"统一纸箱规格"——A 装箱 B 拆箱都用同一种箱子，谁都不用猜。
- **验收**：所有模块的输入输出都只说这些类型，不偷偷传别的（阶段 D2 起全程）。

#### 3.2.3 algo_params.h —— 算法参数的"唯一真源"

- **角色**：算法侧所有数字参数（采样率、FFT 点数、窗型、频段划分、报警阈值）的登记处。
- **接收**：不接收运行数据；由 PC 端 `gen_config_header.py` **根据 config.json 自动生成**（不要手改，会被覆盖）。
- **处理**：无运行逻辑，只是把参数写成宏/常量。
- **发送**：dsp_window / dsp_fft / feat_extract / decision 读取这些参数。
- **为什么重要**：PC 训练算特征和板子上跑推理必须用同一套参数——否则"训练 98%、板上 60%"。所以 config.json 是唯一真源，这份头文件只是它的"复印件"。
- **验收**：改算法参数只动 config.json → 重新生成 → 固件与 Python 行为一致（阶段 D4–D7）。

#### 3.2.4 app_main.c —— 系统"总指挥 / 状态机"

- **角色**：系统大脑与调度员：开机把各模块初始化好，按状态机节奏指挥全流程。
- **接收**：上电事件；采样完成标志/中断；按键事件（复位报警/切页）。
- **处理**：①依次初始化 mpu/i2c/uart/lcd/alarm；②主循环维护状态机：空闲 → 采满一窗 → 分析 → 报警确认 / 正常，按状态调用各模块的"一步"函数；③处理超时与复位。
- **发送**：调用并协调各模块（它是调用者；数据本身由各模块直接传递）。
- **类比**：工地工长——不亲自搬砖，但排班、催进度、处理突发。
- **验收**：从点灯到完整闭环，每一步都能在主循环里走到（阶段：全程）。

#### 3.2.5 bsp_i2c.c —— 与 MPU6050 通信的"电话线"

- **角色**：I2C 总线底层驱动，负责"写寄存器 / 读寄存器"两个原子动作。
- **接收**：来自 bsp_mpu6050 的请求：要读/写哪个寄存器（地址 + 寄存器号）。
- **处理**：用 HAL 的 I2C + DMA 发起一次事务；处理应答/超时错误；保证同一时刻只有一个读写请求。
- **发送**：把读到的字节返回给调用方（bsp_mpu6050）；把要写的字节发给 MPU6050。
- **依赖**：HAL I2C、DMA、project_config 的引脚定义。
- **类比**：邮差只负责"把信送到这个门牌"，不知道信里写什么。
- **验收**：能稳定读到 WHO_AM_I = 0x68（阶段 D2）。

#### 3.2.6 bsp_mpu6050.c —— 传感器的"翻译官"

- **角色**：把 MPU6050 配置好并把原始加速度读出来，是整条信号链的**源头**。
- **接收**：app_main 的初始化/采样指令；bsp_i2c 读回的寄存器字节。
- **处理**：①配置寄存器：电源(PWR_MGMT_1)、量程(±2g)、ODR 1 kHz、DLPF、使能 FIFO；②把 FIFO 原始字节解析成三轴 int16（每样本 6 字节）；③FIFO"水印满"时批量读出，保证等间隔、不丢点。
- **发送**：把连续 `accel_t` 样本送给两个去处：**实时推理**→ 算法链上游缓冲；**采集模式**→ stream_mode 打包上送 PC。
- **依赖**：bsp_i2c、project_config、algo_params（ODR 等）。
- **类比**：温度计——不管温度怎么用，只负责"把物理振动变成数字"且按时读数。
- **验收**：串口打印数值随敲击/晃动明显变化；采样间隔稳定（阶段 D2–D3）。

#### 3.2.7 dsp_window.c —— 加窗预处理

- **角色**：FFT 之前把截取的一段数据"修整"一下，降低频谱泄漏（谱峰拖尾）。
- **接收**：一段连续原始加速度（float，1024 点，来自双缓冲/滑窗）。
- **处理**：生成/存储 Hann 窗系数表；把窗系数与数据**逐点相乘**。
- **发送**：加窗后的 1024 点数组给 dsp_fft。
- **依赖**：algo_params（窗长、窗型）。
- **类比**：拍照前对焦——不加窗频谱"糊"，加窗后谱峰又尖又干净。
- **验收**：单频信号频谱旁瓣明显变小（PC 对照可见，阶段 D4）。

#### 3.2.8 dsp_fft.c —— 时域→频域的"翻译官"

- **角色**：把"随时间变化的振动波形"变成"各频率成分有多强"的频谱，是判断故障的核心工具。
- **接收**：加窗后的 1024 点数组（来自 dsp_window）。
- **处理**：调用 CMSIS-DSP 的 `arm_rfft_fast_f32` 做 1024 点实数 FFT；从复数结果算幅度谱（0~500 Hz）；可顺带累计低/中/高频段能量。
- **发送**：`spectrum_t` 给两个下游：feat_extract（提特征）与 ui_screen（画实时频谱）。
- **依赖**：CMSIS-DSP、algo_params（点数）。
- **类比**：把一段声音拆成"钢琴键盘上每个键各自响了多大"——找故障就是找"哪个键（频率）突然变响了"。
- **验收**：风扇贴片后，1× 转速峰明显变高（PC 频谱图可见，阶段 D4）。

#### 3.2.9 feat_extract.c —— 特征"提炼师"

- **角色**：把几百个频点浓缩成十几个有物理意义的数字（特征向量）供 AI 使用；让结果"可解释"。
- **接收**：`spectrum_t`（来自 dsp_fft）；可再加时域统计量（RMS/峭度，从原始窗数据算）。
- **处理**：按 algo_params 的频段定义计算：①找 1× 转速峰并估计 f0；②A(1×)/总能量（不平衡指标）；③A(2×)/A(1×)；④低/中/高频段能量占比；⑤RMS、峭度、峰值因子 → 得 `feature_t`（10~16 维）+ f0。**算法必须与 PC 端 features_py.py 逐行一致**。
- **发送**：`feature_t` 给 ai_infer（模型输入）与 app_debug（打印查看）。
- **依赖**：dsp_fft、algo_params、types。
- **类比**：医生把几十项化验浓缩成"几个关键指标"再下判断——特征就是"振动化验单"。
- **验收**：同一段数据，固件与 features_py 算出的特征一致（阶段 D7）。

#### 3.2.10 model_net.c —— AI 网络本体（X-CUBE-AI 生成，不手写）

- **角色**：训练好的神经网络（含权重）的 C 实现，由 X-CUBE-AI 从 ONNX/TFLite **自动生成**。
- **接收 / 发送**：只暴露 `ai_run(输入张量, 输出张量)` 接口，张量由 ai_infer 填好/取走。
- **处理**：执行各层前向计算（int8 量化乘加）——内部细节不需要你懂，工具保证正确。
- **依赖**：X-CUBE-AI 生成的 network.c/h + 校准数据。
- **类比**：买来的成品发动机——你只管踩油门（喂特征）看转速（拿概率），不用自己造。
- **验收**：编译通过；工具报告 ROM/RAM/周期数符合预算（阶段 D9）。

#### 3.2.11 ai_infer.c —— 推理"小助手"

- **角色**：模型与业务之间的适配层：把 feature_t 喂给模型、取出 3 类概率，顺手记录推理耗时（面试指标来源）。
- **接收**：`feature_t`（来自 feat_extract）。
- **处理**：①把特征填进 model_net 输入张量（缩放要与训练一致）；②调用 ai_run；③取出 `prob_t`（3 类概率）；④用 DWT 计推理耗时微秒数（回填 相关页面）。
- **发送**：`prob_t` 给 decision；耗时数字给 app_debug。
- **类比**：化验科窗口——递进样本，拿出"三档概率报告"，还标了用时。
- **验收**：同一段数据，板上概率与 PC float 结果接近（量化损失 <2~3%，阶段 D9）。

#### 3.2.12 decision.c —— "拍板者 / 防抖裁判"

- **角色**：不轻信单次判断：对概率做平滑与滞回，输出稳定结论，防止"一抖就报警"。
- **接收**：每 0.5 s 一次的 `prob_t`（来自 ai_infer）。
- **处理**：①概率 EMA 平滑或"最近 5 窗投票"；②滞回：连续 K 窗异常才报，连续 M 窗正常（或按键复位）才恢复；阈值都在 algo_params。
- **发送**：`decision_t`（状态+置信度+f0）给 ui_screen（显示）、act_alarm（执行）、app_debug（日志）。
- **类比**：质量主管——一个人喊"坏了"不算，连续几个人一致才算；确认恢复才销警。
- **验收**：贴片 → ≤2 s 报警；撕掉 → 恢复；正常态 10 min 无误报（阶段 D10）。

#### 3.2.13 ui_screen.c —— 前台"讲解员"

- **角色**：把内部结论变成人能看的画面：状态大字、置信度、实时频谱、统计页。
- **接收**：`decision_t`、`spectrum_t`（频谱页）、按键/触摸事件（切页）。
- **处理**：调官方 lcd.c 画大字/柱状频谱；异常状态大字变红闪烁；维护页面切换；放在主循环低优先级，不抢占采样。
- **发送**：无数据输出（纯展示）。
- **依赖**：官方 lcd.c + 字库（复用例程）。
- **类比**：航班信息屏——内容由后台决定，它负责让旅客一眼看懂。
- **验收**：屏幕状态随 decision 变化，演示肉眼可辨（阶段 D10）。

#### 3.2.14 act_alarm.c —— 报警"执行者"

- **角色**：把决策变成物理动作：蜂鸣器、继电器断开演示负载、LED。
- **接收**：`decision_t`（来自 decision）。
- **处理**：①异常 → 蜂鸣器间歇 1 Hz、继电器动作、LED 翻转；②恢复正常 → 停止声光（或等手动复位）；③报警后最少持续 N 秒，避免快速闪断。
- **发送**：控制 GPIO（BEEP/继电器/LED）。
- **依赖**：板载 BSP（官方例程宏）。
- **类比**：火警铃 + 自动断电闸——"决定报警"的是系统，它负责真响铃断电。
- **验收**：报警时声光联动、负载被断开；恢复时解除（阶段 D10）。

#### 3.2.15 link_frame.c + link_uart.c + stream_mode.c —— 数据链路的"打包员 / 干线 / 采集管理员"

- **link_frame.c（打包/拆包员）**：帧格式的编解码。**接收**：stream_mode 的原始样本块（上行）、link_uart 收到的下行字节。**处理**：上行 = 加帧头(0x5A 0x5A)+类型+长度+CRC；下行 = 校验后解析指令（开始/停止/设标签）。**发送**：打包帧给 link_uart 发出；指令给 stream_mode。
- **link_uart.c（快递干线）**：串口 + DMA 底层。**接收**：要发的字节（来自 link_frame）与 UART 收到的字节。**处理**：DMA + 环形队列解耦收发，统计丢包。**发送**：收到的完整字节给 link_frame 拆包。
- **stream_mode.c（采集管理员）**：**接收**：app_main 的"进入采集模式"指令 + MPU6050 连续样本。**处理**：持续采样，攒够一块就交给 link_frame 打包；收停止/切标签指令时退出/改标签。**发送**：原始样本帧流给 PC（collect.py 接收）。
- **三者类比**：产品出厂流水线——stream 是车间（攒货）、frame 是包装工（装箱贴单）、uart 是货车（运输）；PC 端 frames.py 是收货拆箱的仓库员。
- **验收**：`python collect.py` 能连续录到完整文件、不丢帧（阶段 D3–D6）。

#### 3.2.16 app_debug.c —— 调试"仪表盘"

- **角色**：贯穿全程的辅助设施：日志、断言、DWT 计时、RAM 统计。
- **接收**：各模块调用 `DBG_LOG(...)` / 断言 / `dwt_us()` 的需求。
- **处理**：按编译开关决定是否输出；用内核 DWT 计数器计时（不占定时器）；可统计内存余量。
- **发送**：格式化日志到串口（调试期开，正式运行可关）。
- **类比**：驾驶舱仪表——平时看飞得稳不稳，出事时黑匣子靠它复盘。
- **验收**：相关页面 的"推理耗时 / 延迟"数字从这里读出来（阶段：全程）。

> 底座清单（**不用自己写**）：HAL 库、CMSIS-DSP 的 `arm_rfft_fast_f32`、X-CUBE-AI 生成的 `network.c/h`、官方 `lcd.c` 与基础库、CubeMX/官方例程骨架。真正从零写的就是上面 App 层 11 个 .c + 4 个公共头。

**PC 模块职责详解（与固件卡片同模板：角色 / 接收 / 处理 / 输出 / 何时用 / 类比）**

#### 3.3.1 config.json —— 标签与数据目录唯一真源（PC 侧）

- **角色**：PC 侧标签枚举、X/Y 轴约定、工况到模型标签映射、正式/调试目录和清单路径的唯一说明；固件采样常量仍以实际 C 工程为准。
- **接收**：由你（或 AI 助手）维护，是人写的文件。
- **处理**：无逻辑，只是 JSON 数据。
- **输出**：喂给 make_dataset / features_py / train_*（训练侧）和 gen_config_header.py（生成固件 algo_params.h）。
- **何时用**：D4 定稿，之后每次改参数只改这里。
- **类比**：全公司唯一的"产品规格书"——研发和生产都照它干活，谁都不许自己改数字。

#### 3.3.2 py_common/frames.py —— 拆箱的"仓库员"

- **角色**：PC 端复刻固件 link_frame 的帧解析逻辑（同一份字节格式）。
- **接收**：串口读到的字节流（来自 serial_link）或存盘的原始文件。
- **处理**：找帧头(0x5A 0x5A)、校验长度与 CRC、把样本负载用 `np.frombuffer` 解成 int16 数组、按帧切块（不完整帧缓存等下一批）。
- **输出**：一帧一帧的样本数组 + 元信息，交给 store / collect / make_dataset。
- **何时用**：D3–D6 采集期；也是等货期"文件模拟串口"练习的主角。
- **类比**：收货仓库拆箱员——货车（串口）拉来整包货，他按箱号（帧头）一件件拆出登记。

#### 3.3.3 py_common/metadata.py —— 数据"契约管理员"

- **角色**：统一解析/校验新旧 CSV 元数据，生成文件名并追加正式数据清单。
- **接收**：采集参数和 `# meta_json=...` 头；旧版 `# k=v` 头只读兼容。
- **处理**：检查工况、证据、可信度、X/Y 轴和采集参数；明确不接受夹具版本、传感器编号、安装点字段。
- **输出**：自描述 CSV 头、`04_数据集/manifest.csv` 行。
- **何时用**：每次采集、检查和训练清单生成。
- **类比**：档案馆的统一表格和验收章。

#### 3.3.4 recv.py —— 串口采集与归档

- **角色**：接收样本帧、统计丢帧、写结构化 CSV。
- **接收**：命令行中的设备/工况/证据/电压等字段和固件上行帧。
- **处理**：先校验元数据，再按 `formal` 或 `debug` 分目录保存；旧 `raw/` 不再写入。
- **输出**：`formal/*.csv + manifest.csv` 或本地 `debug_raw/*.csv`，日志写入 `05_演示与输出/boardlog/`。
- **何时用**：每次真实采集。
- **类比**：带验收单的档案室管理员。

#### 3.3.5 plot_check.py / peak_check.py —— 检查与对拍

- **角色**：离线快速检查时域、频谱、峰值和标签摘要。
- **接收**：formal/debug/legacy CSV。
- **处理**：通过 metadata.py 统一读取新旧头，FFT 与板上口径对拍。
- **输出**：终端摘要和演示频谱图。
- **何时用**：每次采集后先检查，再决定是否把 `quality_status` 改为 `pass`。

#### 3.3.6 vis.py —— 调试"监视器"

- **角色**：实时画出波形/频谱，让你"看得见"数据对不对。
- **接收**：串口实时帧（与 collect 类似）或离线读文件。
- **处理**：用 matplotlib 动画刷新两个子图：上面原始波形、下面实时频谱（滑动窗 FFT）。
- **输出**：屏幕上的图（也可存截图给 README）。
- **何时用**：D3–D4 验证采集与 FFT；D10 演示也可用它投影。
- **类比**：心电图监护屏——不诊断，只让你看到心跳长什么样。

#### 3.3.7 make_dataset.py —— 训练清单的"加工厂"

- **角色**：从 `manifest.csv` 选出通过质检的正式样本，并按设备生成可复现 train/test 清单。
- **接收**：formal CSV 的 manifest 行和 config.json 约定。
- **处理**：排除 pending/reject/unassigned，默认排除 suspect；按 `device_id` 留出测试设备，防止窗口泄漏。
- **输出**：`04_数据集/processed/split_manifest.csv` 和 `summary.json`；特征/npz 后续在此基础上扩展。
- **何时用**：D6–D7。
- **类比**：中央厨房——把采购来的菜（raw）洗切配好分装（npz），还按"哪家餐厅用"（设备）分餐，防止串味（过拟合）。

#### 3.3.8 features_py.py —— 特征的"裁判员副本"

- **角色**：在 PC 上用同一参数把特征算法实现一遍，用于与固件 feat_extract.c 对拍。
- **接收**：一段原始窗数据 + config.json。
- **处理**：按与固件完全一致的步骤算特征（f0、1×/2× 峰比、频段能量、RMS、峭度…）。
- **输出**：特征向量；和固件输出对比（一致性检查脚本）。
- **何时用**：D7 校验点（固件算出来的特征必须和它一致）。
- **类比**：两份独立做的账本对账——一致才说明两边都没算错。

#### 3.3.9 train_feature.py —— 训练"教练"（路线 A，推荐先做）

- **角色**：用切好的特征样本训练一个轻量 MLP（scikit-learn），得到 3 分类模型。
- **接收**：make_dataset 的 train/val .npz。
- **处理**：标准化特征 → 训练 MLP → 输出混淆矩阵与每类召回率 → 保存模型。
- **输出**：模型文件（onnx/tflite 待导出）+ 训练日志。
- **何时用**：D7。
- **类比**：驾校教练——拿一堆"正常/不平衡/机械松动"的样本练习卷教模型怎么判。

#### 3.3.10 train_cnn.py —— 训练"教练"（路线 B，可选）

- **角色**：用频谱做输入训练 1D-CNN（PyTorch/TF），路线 A 不满足时再上。
- **接收/处理/输出**：同 train_feature，但输入换成频谱、模型换成 CNN。
- **何时用**：D8（时间紧可跳过，见 相关页面 砍法）。

#### 3.3.11 eval.py —— 毕业考"考官"

- **角色**：在从没见过的留出风扇 B 上评估模型，给出跨设备测试数字。
- **接收**：模型 + 测试集 .npz。
- **处理**：逐样本预测 → 混淆矩阵、每类 precision/recall、留出设备准确率 → 生成指标 CSV/图。
- **输出**：05_演示与输出/ 的评估报告（这是简历数字的来源）。
- **何时用**：D8（离线）/ D11（板上泛化复测）。
- **类比**：换一个陌生考场考试——考得好才说明真学会了，而不是背下了原题。

#### 3.3.12 quant_export.py —— 模型"打包发货员"

- **角色**：把 float 模型压成 int8 并导出 X-CUBE-AI 能导入的格式（ONNX/TFLite）。
- **接收**：训练好的模型 + 校准集（一小段真实数据）。
- **处理**：做 PTQ 量化（int8）→ 评估量化后精度损失 → 导出 ONNX/TFLite。
- **输出**：05_演示与输出/models/ 下的量化模型文件。
- **何时用**：D8。
- **类比**：把大行李箱压缩成登机箱（4 倍小）——压完要当场称重验货（评估损失），合格才发货。

#### 3.3.13 gen_config_header.py —— 固件参数"复印机"

- **角色**：把 config.json 翻译成固件的 algo_params.h，保证两边参数永远一致。
- **接收**：config.json。
- **处理**：读取 JSON → 生成带注释的 C 头文件文本 → 写入 02_固件/App/algo_params.h。
- **输出**：algo_params.h（固件编译时使用）。
- **何时用**：D4 起，每次改参数后重跑一次。
- **类比**：复印机——源文件（json）改了，重新复印一份（h）给固件，两边永远不会对不上。

### 3.4 关键契约

```c
/* types.h（示意） */
typedef struct { int16_t x, y, z; } accel_t;        /* 原始加速度 */
typedef struct { float mag[512]; } spectrum_t;      /* 幅度谱 0~512Hz */
typedef float feature_t[16];                         /* 特征向量 */
typedef struct { float p[3]; } prob_t;               /* 3 类概率 */
typedef enum { ST_NORMAL, ST_UNBALANCE, ST_BEARING, ST_INVALID } state_t;
typedef struct { state_t st; float conf; float f0_hz; } decision_t;
/* 上行样本帧：0x5A 0xA5 TYPE LEN(int16样本数) samples... CRC16 */
/* 下行指令帧：0xA5 0x5A CMD(0x01起 0x02停 0x03标类) PAYLOAD CRC16 */
```

### 3.5 最小可跑路径

1. project_config + types + app_debug（骨架跑通打印）；

2. bsp_i2c → bsp_mpu6050：串口打印原始加速度（出数）；

3. link_uart + link_frame + stream_mode：原始数据打帧上送 PC（= D3–D5 采集链路）；

4. dsp_window + dsp_fft + feat_extract：同一段数据与 PC 端 features_py 对照一致（D4/D7 校验点）；

5. PC：采集→make_dataset→train_feature→quant_export→X-CUBE-AI 生成 model_net；

6. ai_infer 接入 → decision → ui_screen + act_alarm（D9–D10 全闭环）。
   
   > 优先让"传感器 → 屏幕/串口"先通，**不要先把 11 个 .c 全部写完再联调**——每步有退出标准（对照 相关页面）。

### 3.6 可复用部分

- 官方例程：lcd/触摸、BEEP/LED/KEY BSP、串口重定向 printf、工程骨架；
- HAL：I2C、UART、DMA、TIM、GPIO、DWT；
- CMSIS-DSP：FFT；X-CUBE-AI：模型转换与板上验证；

### 3.7 单窗口处理过程

**场景 A：实时检测（到货后 D9–D10 要跑通的链路）**

1. **bsp_mpu6050** 每 1 ms 读到一个三轴样本（FIFO 帮它攒着，攒满一批唤醒它），放进双缓冲（一个在写、一个在读，互不打断）；
2. 主循环发现"读缓冲攒满 1024 点 ≈ 1 秒" → 交给 **dsp_window**：这段波形先乘一遍 Hann 窗；
3. **dsp_fft** 把加窗后的 1024 点变成幅度谱（0~500 Hz 共 512 个频点），一份给 **ui_screen** 画图，一份给 **feat_extract**；
4. **feat_extract** 按 algo_params 把频谱浓缩成 12 个特征（含 1× 峰、频段能量、RMS、峭度…），这就是**模型的一句话描述**；
5. **ai_infer** 把 12 个特征喂给 **model_net**（X-CUBE-AI 生成的网络），0.5 秒内拿到"正常 3% / 不平衡 92% / 机械松动 5%"这样的 prob_t（三类概率），并记下耗时；
6. **decision** 不马上信：和之前几窗一起投票 + 过滞回线 → 才输出 decision_t = "不平衡（置信 92%，f0=45 Hz）"；
7. **ui_screen** 把大字变红显示"不平衡"并画频谱；**act_alarm** 让蜂鸣器间歇响、继电器断开演示负载；
8. 全程 **app_debug** 在串口打日志、用 DWT 记下"这一窗从 FFT 到出结论花了多少微秒"——这就是简历上的数字。

**场景 B：建数据集（D5–D6）**

1. 你把风扇 A 调到 9 V、贴好胶带（不平衡），在 PC 敲：`python collect.py --label 1 --dev A --vol 9V --sec 30`；
2. **serial_link** 发"开始 + 标签 1"指令；固件 **stream_mode** 收到后进入采集模式，**bsp_mpu6050** 持续采样；
3. 固件每攒 128 个样本就交给 **link_frame** 打包 → **link_uart** 发出 → PC 端 **frames.py** 拆包还原 → **store.py** 落成 `unbalance_扇A_9V_01.bin` 并登记 meta.csv；
4. 30 秒到，脚本发"停止"，这段带标签的原始数据入库；
5. 重复几十段（不同风扇/转速/状态/故障档位）后，**make_dataset** 把全部 .bin 滑窗切样并**按设备**切成 train/val/test；
6. **features_py** 用和固件一致的算法算特征 → **train_feature** 训练 → **eval** 在留出的陌生风扇上考试 → **quant_export** 压成 int8 → **gen_config_header** 生成 algo_params.h → 固件拿到和训练完全一致的参数 → 回到场景 A 闭环。

> 一句话记忆：**固件 11 个 .c = 一条从左到右的信号流水线；PC 13 个文件 = 一条从右到左的"造数据→训练→部署"流水线；两条线靠 config.json 和帧格式这两份"契约"对齐。**
